# Phase 26 — SoEditor 0.7 SDK and Release Hardening

## Status

COMPLETE.

## Goal

Produce a coherent, owner-reviewable SoEditor `0.7.0` structured-extension
candidate without performing an unauthorized npm publication, tag, or hosted
release.

## Sources of truth

- `AGENTS.md`
- `docs/PRODUCT.md`
- `docs/architecture.md`
- `docs/ROADMAP.md`
- `docs/DEVELOPMENT-POLICY.md`
- accepted ADRs, especially 0024–0026
- completed Phase 23–25 prompts and implementation

## Required implementation

1. Classify the 0.7 package-root and extension-author API surface as
   application public, extension-author public, experimental, or internal.
   Keep the SDK curated and expose every generic contract required to implement
   a command-backed third-party structured widget without private imports.
2. Add a clean packed-package third-party widget consumer that registers a
   custom conversion and node view, reads/replaces immutable structured
   content through the public visual service, builds under strict TypeScript
   and Vite, and runs its lifecycle in Chromium.
3. Align the workspace and all 17 public packages at `0.7.0`, refresh the
   lockfile, and update release/registry tooling for the aligned 0.7 line while
   retaining exact package-count, scope, metadata, export-map, and
   unpublished-version guards.
4. Complete the 0.6-to-0.7 migration guide and synchronize the changelog,
   README, status, distribution, release operations, plugin guide,
   architecture, and version language. Clearly distinguish a verified local
   candidate from a published release.
5. Exercise strict packed NodeNext/native ESM, normal and narrow Vite, the
   third-party widget consumer, Classic/Developer/Markdown/CMS configurations,
   security, readonly, history, clipboard, accessibility, teardown, repeated
   lifecycle, and measured bundle/performance budgets.
6. Run lint, strict typecheck, unit/consumer/distribution/release/Chromium
   tests, build, license verification, high-severity dependency audit, npm
   publication dry run, and the read-only registry availability preflight from
   the aligned candidate.
7. Perform a final read-only adversarial review. Fix every Critical and High
   finding and record accepted Medium/Low limitations in `docs/status.md`.

## Release boundary

The following remain owner-controlled and are not authorized by this phase:

- `pnpm release:publish`;
- creating or pushing a `v0.7.0` tag;
- creating a GitHub Release;
- changing the MIT license, npm identity/scope, token, or protected-environment
  policy;
- claiming registry or CDN availability before an authorized publication and
  external verification.

## Explicitly deferred

- mapped annotations/comments and revision review (Phases 27–28);
- collaboration, workspace/framework adapters, and plugin marketplace work;
- expanding tables into spreadsheets or media into arbitrary executable
  embeds.

## Definition of Done

- all 17 candidate packages are aligned at `0.7.0` with coherent docs and a
  complete dry-run artifact set;
- a clean packed consumer proves a third-party structured widget using only
  documented package roots and curated SDK contracts;
- every local release gate and the read-only registry preflight pass;
- Critical = 0 and High = 0;
- the reviewed commit is pushed while actual publication/tag/release remains
  explicitly pending owner authorization.
